# Domain Heuristics Guide

领域分析启发式指南。Phase G1 中使用此文件进行 6 维度分析。

---

## 维度 1: 时间敏感性 (Time Sensitivity)

### 启发式问题

- 该领域的时间信息需要精确到什么级别？（天 / 小时 / 分钟）
- 是否有"时段"概念？（如午市/晚市 -> 上午号/下午号 / 工作日/周末）
- 是否有"截止时间"？（如 last order -> 挂号截止时间 / 预约截止时间）
- 时间冲突的后果有多严重？（错过时段 -> 无法就诊 vs 等位 10 分钟）

### 分级标准

| 等级 | 特征 | 示例领域 |
|------|------|----------|
| **high** | 精确到分钟，错过即失败 | 医院挂号、航班值机、考试报名 |
| **medium** | 精确到小时/时段，有缓冲 | 餐厅订位、家政预约、美容预约 |
| **low** | 精确到天，灵活度高 | 汽修预约、家政保洁、设备维修 |

### 对模块设计的影响

- high -> 模块一的 time 字段为 datetime 类型，必填，模块四需二次确认
- medium -> time 字段可以是 datetime 或 date + timeslot enum
- low -> time 字段可以是 date，模块四确认即可

## 维度 2: 对象可变性 (Object Volatility)

### 启发式问题

- 交互对象的属性（评分/价格/排队）是实时变化的还是相对固定的？
- 用户需要知道的哪些信息只有交互对象自己才知道？
- 是否存在"信息过期"问题？（如排队时间 30 分钟后可能完全不同）

### 分级标准

| 等级 | 特征 | 示例领域 |
|------|------|----------|
| **high** | 排队/可用性实时变化 | 餐厅（排队）、医院（号源）、理发店（排队） |
| **medium** | 部分属性变化，部分固定 | 家政（阿姨档期）、美容（技师空档）、汽修（工位） |
| **low** | 属性相对固定 | 政务办事（流程固定）、教育培训（课程表固定） |

### 对模块设计的影响

- high -> 模块二中增加"容忍度"字段（如 max_queue_minutes），Phase 4 必须实时确认
- medium -> 模块二中增加"可用性确认"字段
- low -> 减少模块二的确认类字段，更多依赖模块一的筛选

## 维度 3: 约束复杂度 (Constraint Complexity)

### 启发式问题

- 该领域有哪些"必须满足"的硬约束？（如宠物友好、无障碍通道）
- 哪些约束之间可能冲突？
- 哪些约束是"隐性"的（用户不会主动说但很重要）？

### 常见约束模式

| 约束类型 | 餐厅领域 | 其他领域示例 |
|----------|----------|-------------|
| **特殊人群** | 孕妇/小孩/老人 | 老人（医院）、婴儿（家政）、残疾人（政务） |
| **设施需求** | 包间/无烟区 | 无障碍通道/电梯/停车位/母婴室 |
| **政策限制** | 宠物政策 | 医保类型/就诊卡/预约资格 |
| **时效容忍** | 排队时间 | 候诊时间/上门时间窗口/取件时间 |
| **偏好匹配** | 菜系/口味 | 医生性别/阿姨籍贯/技师手艺 |

### 冲突发现方法

1. **两两组合法**：将模块二的所有 boolean/enum 字段做两两组合，判断是否矛盾
2. **领域经验法**：基于领域常识判断已知冲突（如"宠物 + 包间"在餐厅领域冲突）
3. **极端值法**：检查极端值组合（如"评分≥4.8 + 人均≤50 + 热门区域"）

### 对模块设计的影响

- high -> 模块二字段 7+ 个，冲突规则 5+ 条，需要内部循环
- medium -> 模块二字段 4-6 个，冲突规则 2-4 条
- low -> 模块二字段 2-3 个，冲突规则 0-1 条

## 维度 4: 增值服务 (Value-Added Services)

### 启发式问题

- 该领域有哪些"可选"的附加服务？
- 哪些服务需要提前预约/确认？
- 哪些服务有额外费用？

### 常见增值服务模式

| 服务类型 | 餐厅领域 | 其他领域示例 |
|----------|----------|-------------|
| **配套服务** | 停车/餐具 | 代驾/陪诊/接送 |
| **定制化** | 生日布置 | 上门服务/特殊护理/加急处理 |
| **确认类** | 低消确认 | 报销凭证/医保类型/保修条款 |
| **升级类** | VIP包间 | 专家号/高级技师/金牌阿姨 |

### 对模块设计的影响

- 每个增值服务 -> 模块三的一个字段（通常是 boolean + condition 的 detail 字段）
- 增值服务多时考虑分组（如"配套服务"和"定制化"分两批询问）

## 维度 5: 信息不对称 (Information Asymmetry)

### 启发式问题

- 用户和交互对象之间，哪些信息只有交互对象才知道？
- 哪些信息是用户需要但无法提前获取的？
- 哪些信息需要通过外呼/交互才能确认？

### 常见不对称信息

| 不对称类型 | 餐厅领域 | 其他领域示例 |
|------------|----------|-------------|
| **实时状态** | 当前排队长度 | 当前号源剩余/当前工位空缺 |
| **政策细节** | 宠物政策/包间低消 | 医保报销比例/保修范围 |
| **可用性** | 某时段是否有位 | 某时段是否有号/某阿姨是否有档期 |
| **费用** | 实际人均/低消金额 | 实际诊疗费/上门费/配件费 |

### 对模块设计的影响

- 不对称信息 -> 用途(2) 与交互对象确认 -> 模块二或模块三
- 实时状态类 -> 模块二的"容忍度"字段 + Phase 4 确认
- 政策细节类 -> 模块三的"确认类"字段 + Phase 4 确认

---

## 维度 6: 失败兜底 (Fallback Patterns)

### 启发式问题

- 交互失败（对象不可用/约束不满足）时的常见备选方案是什么？
- 是否有"替代对象"？（如换一家餐厅 -> 换一家医院/换一个时段）
- 是否有"降级方案"？（如取消包间要求 -> 取消专家号改普通号）

### 常见兜底模式

| 兜底类型 | 餐厅领域 | 其他领域示例 |
|----------|----------|-------------|
| **替代对象** | 换一家餐厅 | 换一家医院/换一个阿姨/换一家店 |
| **降级约束** | 取消包间/放宽排队 | 改普通号/接受非首选时段 |
| **调整时间** | 错峰用餐 | 改天就诊/改天上门/延后维修 |
| **替代渠道** | 外卖替代堂食 | 线上问诊替代线下/自助替代人工 |

### 对模块设计的影响

- 兜底方案 -> Phase 5 的 alternatives 字段 + 模块四的早终止条件
- 替代对象 -> Phase 2 的 on_multi 策略（保留候选列表）
- 降级约束 -> 模块二的冲突消解方案中提供"降级"选项

## 领域分析 Checklist

完成 G1 领域分析时，确认以下都已覆盖：

- [ ] 时间敏感性已分级，time 字段类型已确定
- [ ] 对象可变性已分级，实时确认需求已明确
- [ ] 约束复杂度已分级，约束字段和冲突模式已列举
- [ ] 增值服务已列举，模块三字段方向已明确
- [ ] 信息不对称项已识别，用途(2)字段已确定
- [ ] 失败兜底模式已列举，Phase 5 alternatives 方向已明确
- [ ] 信息项已按 3 种用途分类（filtering / confirmation / post_judgment）
